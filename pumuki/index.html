Stack My Architecture — Curso Pumuki

Quinto curso del ecosistema Stack My Architecture: Pumuki como capa de enforcement determinista (Facts → Rules → Gate → evidencia v2.1) en repos reales.

Público objetivo

Equipos que ya gobiernan el cambio con Governance y/o ejecutan flujo SDD + IA, y quieren operar hooks, CLI, CI y remediaciones sin confundir enforcement con arquitectura de producto.

Prerrequisitos recomendados

  • Curso Governance (AGENTS.md, skills, gates, release) o experiencia equivalente.
  • Curso IA + SDD (OpenSpec, validación, cierre de tickets) o experiencia equivalente.

Este curso no reenseña OpenSpec ni ADR: enlaza a esos cursos y se centra en CLI, perfiles de adopción, doctor, parity CI y evidencia exportable.

Versión mínima del paquete npm

  • pumuki >= 6.3.71 (MVP del curso; repinear cuando el producto publique una release estable posterior).

Lab de práctica

Por defecto se trabaja sobre una variante o fork del proyecto del curso Governance (GovernanceKit) o del curso SDD (HelpdeskSDD), para no inventar dominio nuevo. Elige uno en 00-preparacion/02-lab-governancekit-helpdesksdd.md y mantenlo durante los módulos 1–7.

python3 scripts/build-html.py

Salida: dist/curso-stack-my-architecture-pumuki.html y dist/index.html.

Bienvenida — Curso Pumuki

Pumuki es la capa de enforcement que se ejecuta en hooks locales, MCP y CI: convierte hechos detectables en reglas, aplica un gate por stages y deja evidencia trazable. No sustituye decisiones de arquitectura ni el método SDD: las integra.

Qué vas a conseguir

  • Contrato claro: qué hace Pumuki y qué queda fuera.
  • Un primer verde en un repo real (install, doctor, status).
  • Tres perfiles de adopción (mínimo, SDD, enterprise) alineados al README del producto.
  • Puente operativo con SDD (PUMUKI_EXPERIMENTAL_SDD, validación) y con Governance (AGENTS.md, skills, GitFlow).
  • Monorepo / CI: scope por prefijos, doctor --parity, expectativas en .pumuki/ci-parity-expected.json.
  • Cierre con checklist de release y export doctor --json.

Documentación canónica del producto

Con el repo ast-intelligence-hooks o el paquete publicado:

  • pumuki en npm
  • Manual de uso: docs/product/USAGE.md
  • Instalación: docs/product/INSTALLATION.md
  • README raíz del producto: README.md

Orden de lectura sugerido

Lab: GovernanceKit vs HelpdeskSDD

El curso asume un proyecto de práctica ya definido en los otros cursos para no inventar dominio.

Opción A — GovernanceKit (recomendada si priorizas policy y gates)

Continúa el hilo del curso Governance: mismo repo o fork donde ya tengas AGENTS.md, skills y rutinas de gate. Pumuki debe convivir con esa política sin duplicar el rol de “fuente de verdad” humana.

Opción B — HelpdeskSDD (recomendada si priorizas OpenSpec y validate)

Continúa el hilo del curso SDD: mismo repo o fork donde ejecutes validate y cierres de ticket. Pumuki debe acoplarse al flujo SDD experimental cuando active PUMUKI_EXPERIMENTAL_SDD.

Decisión

Documenta en una línea tu elección y el path del repo:

  • Lab elegido: GovernanceKit / HelpdeskSDD
  • Ruta local del clone: ________________________

Mantén la misma elección hasta el módulo 7.

docs/playbook-pumuki-sdd-bridge.md

Playbook — Puente SDD ↔ Pumuki

Objetivo: cuando el flujo OpenSpec del curso IA + SDD entra en fase de verificación o cierre, Pumuki debe dar señales accionables sin sustituir el Kanban ni las specs.

Activación

  • Variable PUMUKI_EXPERIMENTAL_SDD: comportamiento experimental alineado al flujo SDD (ver docs/product/USAGE.md en ast-intelligence-hooks).

Comandos de comprobación

  • npx pumuki sdd status / rutas documentadas en USAGE.md para validación SDD.
  • Interpretar códigos OPENSPEC_ y SDD_: cada código debe mapearse a una acción concreta (corregir spec, ampliar tests, desbloquear gate, etc.).

Enlace pedagógico

En el curso SDD, usa el playbook Kanban y las semanas de verificación como marco temporal; en este curso solo registras qué parte del output de Pumuki alimenta el cierre del ticket.

No hacer aquí

  • No redactar OpenSpec completo ni ADR: vuelve al curso SDD o Governance.
02-modulos/01-contrato-y-limites.md

Módulo 1 — Contrato y límites

Qué es Pumuki

Pipeline por stages (PRE_WRITE, PRE_COMMIT, PRE_PUSH, CI, …): Facts → Rules → Gate → evidencia versionada.

Qué no es

  • No define la arquitectura de tu app iOS/Android ni sustituye ADR.
  • No reemplaza el criterio humano de revisión ni el método SDD completo.

Lectura

  • README.md del producto: límites y posicionamiento.
  • docs/product/USAGE.md: stages, comandos y variables relevantes.

Ejercicio

En tu lab, enumera tres facts que ya detecta Pumuki en un archivo de ejemplo y qué regla los bloquearía o advertiría.

02-modulos/02-instalacion-y-primer-verde.md

Módulo 2 — Instalación y primer verde

Objetivo

Dejar el consumidor con install aplicado, doctor sin bloqueos críticos y status coherente con la versión mínima (>= 6.3.71).

Comandos

npx pumuki install
npx pumuki doctor
npx pumuki status

Postinstall

El paquete define postinstall hacia el instalador; si falla en CI, revisa docs/product/INSTALLATION.md.

Troubleshooting

  • pathExecutionHazard y rutas: revisa USAGE.md y mensajes de doctor (paths duplicados, binarios equivocados).
  • Cualquier hint operativo nuevo en tu versión: CHANGELOG.md del producto.

Ejercicio

Captura salida de doctor --json en el lab antes y después de corregir un problema menor (por ejemplo path o hook desalineado).

02-modulos/07-proyecto-final-checklist.md

Módulo 7 — Proyecto final (checklist release)

Checklist mínima

  • ☐ Versión efectiva pumuki >= 6.3.71 (status / doctor).
  • ☐ Hooks y CI alineados al perfil elegido (módulo 3).
  • ☐ Sin bloqueos críticos en doctor; warnings justificados documentados.
  • ☐ Evidencia v2.1 coherente con el contrato (docs/mcp/ai-evidence-v2.1-contract.md en el producto).
  • ☐ Export doctor --json archivado en el lugar que defina tu equipo (no commitear secretos).

Entrega

Un solo documento en el lab (o comentario de PR) con: perfil, versión, ruta del JSON exportado (o artefacto CI), y enlace al curso hub /pumuki/ cuando esté publicado.
